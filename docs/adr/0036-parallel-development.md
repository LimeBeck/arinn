# ADR-0036: Parallel development by several agents

- **Status:** Accepted
- **Date:** 2026-09-28
- **Deciders:** project owner
- **Amends / Supersedes:** amends [ADR-0028](0028-documentation-governance.md) (specification versioning, ADR numbering) and [ADR-0033](0033-ci-cd-and-releases.md) (changelog, merging)
- **Amended by / Superseded by:** —
- **Specification:** [§1.2, §17.1](../specifications/arinn-specification.md)

## Context

Several AI coding agents (Claude Code, Codex) and people are expected to work on Arinn at the same time. Merge conflicts come mostly from files that almost every pull request touches: `CHANGELOG.md`, the ADR register and the next free ADR number, the specification version, `ROADMAP.md`, `Cargo.lock`, large source files and the shared protocol. Two pull requests can also be green on their own and break each other once merged.

## Decision

**Work units.** One issue = one task = one agent = one branch = one pull request. An issue created from the *Agent task* template names the requirement IDs, the **zone** (paths the task may change), shared files it must touch, its dependencies and, if needed, a **reserved ADR number**. An agent claims an issue by assigning it and adding a label `agent:<name>`; claimed issues are not taken by anyone else. Tasks that depend on an open question (OQ-xx) or another issue wait.

**Split along architecture boundaries.** Contracts first: a change to `crates/arinn-protocol`, the plugin SDK or interface XML in `docs/plugin-api/` is its own pull request labelled `contract-change`, and only one such pull request is open at a time. After it merges, providers, shell screens on the demo provider and platform work proceed in parallel, because they meet only through that contract. A large single file is split into modules in its own pull request before several tasks work in it at once (Phase 1 already split the daemon's `main.rs`; `runtime.rs` is the largest file today).

**Conflict-free shared files.**

| File | Rule |
| --- | --- |
| `CHANGELOG.md` | Pull requests add a fragment file under `changes/<category>/`; `scripts/release.py collect` builds the release section. |
| ADR numbers | Reserved in the issue before work starts; `scripts/adr.py check` fails CI on duplicates. |
| `docs/adr/README.md` register | Generated by `scripts/adr.py register`; conflicts are resolved by rerunning it. |
| Specification version | Bumped by the maintainer when preparing a release, not in every pull request; §22 is updated at the same time. |
| `ROADMAP.md` | A pull request changes only the rows of its own gates; phase status is changed by the maintainer. |
| `Cargo.lock` | Never merged by hand; regenerate with `cargo` after merging `master`. |

**Integration.** Branches are short-lived and merge `master` regularly; nobody rewrites another branch's history. Branch protection requires branches to be up to date with `master` before merging, so CI always runs on the merged result. If the repository moves to an organization, a GitHub merge queue replaces that rule. `.github/CODEOWNERS` requests the maintainer's review for contracts, specification, ADRs, roadmap and pipelines.

**Agent commits and the CLA.** Agents operated by the maintainer commit under their own git identity (for example `Claude <noreply@anthropic.com>`), which has no GitHub account and cannot sign the CLA. Their work is directed and reviewed by the maintainer and covered by the maintainer's rights, so these identities are on the CLA allowlist. Agents run by other contributors commit under that contributor's identity or add it as co-author, and the contributor signs the CLA.

**Isolation.** Each agent works in its own clone, worktree or cloud session with its own `target/` and `build/`. Automated tests already use private D-Bus buses and run in parallel safely. Operator tests use fixed unit names and the live desktop; they run one at a time, only with the owner's permission.

## Consequences

Parallel pull requests no longer collide on the changelog, ADR numbers or the specification version. Every task needs an issue before work starts, which adds a little planning overhead. Merging requires an up-to-date branch, so busy periods cause extra CI runs until a merge queue is available.

## Alternatives considered

- Everyone edits `CHANGELOG.md` directly: constant conflicts.
- Assign ADR numbers at merge time: links inside the pull request would change after review.
- Merge without up-to-date branches: semantic conflicts reach `master`.

## Verification

`scripts/check-docs.py` (ADR duplicates, register freshness, fragment format), the `changelog` CI check on pull requests, and branch protection settings on GitHub.
