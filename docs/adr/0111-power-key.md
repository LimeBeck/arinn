## Context

While Arinn runs, the remote's ⏻ key (evdev `KEY_POWER`, Qt `Key_PowerOff`, X11 `XF86PowerOff`) opens Arinn's power menu instead of the desktop's power dialog (§5.7 *Power button*). The platform layer owns the key as a global key, like Home. Over an Activity the shell comes up as for Home with the power menu open, and closing the menu leaves the shell on Home (§6.3). Pressing the key again keeps the menu open. During ambient the key ends ambient and opens the menu. While the session is locked it opens nothing. Every action in the menu keeps its confirmation and its inhibitor and permission reporting ([ADR-0108](0108-system-control.md)); the key itself never suspends or powers off.

The desktop's power handling must not act on the key at the same time, and Arinn may arrange that only while it runs, "through an inhibitor or a setting scoped to the running Arinn session", never by a permanent change of the user's desktop settings.

Three parties can react to `KEY_POWER`:

- **systemd-logind** reads the key from the input device itself and acts on it (`HandlePowerKey=`, `poweroff` by default) unless a process holds a `handle-power-key` block inhibitor.
- **Plasma PowerDevil** holds that inhibitor and reacts through two KGlobalAccel actions of the component `org_kde_powerdevil`: `PowerOff` (`Key_PowerOff`) and `PowerDown` (`Key_PowerDown`). On Wayland KWin turns a short press of `Key_PowerOff` into `Key_PowerOff` on release and a press held for one second into `Key_PowerDown`; on KDE/X11 KGlobalAccel sees `XF86PowerOff` directly. The action then runs the profile's *When power button pressed* choice (by default the logout screen). On the lock screen KWin lets `Key_PowerOff` through to global shortcuts.
- **xfce4-power-manager** grabs `XF86PowerOff` on the root window with `XGrabKey` and holds the logind inhibitor unless `logind-handle-power-key` is set.

The shell needs to know that a press is a power-key press and not Home. It must not infer that from `Status` or `Changed` ([ADR-0069](0069-explicit-home-presentation-requests.md)). [ADR-0106](0106-quick-menu-presentation.md) gave the quick-menu key its own request pair for the same reason and rejected a request kind; it records that the power key adds its own additive pair.

## Decision

**Contract.** `org.arinn.Daemon1` gains two members; every existing signature stays:

- `ReportPowerMenuRequest(target: s, output: s)` has the authentication and validation of `ReportHomeRequest` and `ReportQuickMenuRequest`: only the current platform adapter may call it, and both strings follow the ordinary-text bounds. It commits the same state as `ReportHomeRequest` (Home visible with that Return target and output), emits `Changed`, then emits one `PowerMenuRequested(epoch: s, target: s, output: s)`, also for identical repeats. After the signal it arms the Activity background capture exactly as `ReportHomeRequest` does ([ADR-0087](0087-bounded-activity-background-frames.md), §12.3): the power menu opens over Home, so the Activity's last frame belongs behind it. A rejected call changes no state, emits nothing and arms nothing.
- `PowerMenuRequested` is a transient presentation intent with the delivery rules of `HomeRequested`: it carries the daemon epoch and the request's opaque Return target and output, and it is never persisted, replayed to a late subscriber or synthesized from a state report. None of the three requests emits another's signal.

`Status` is unchanged. While the power menu is open the platform state is the Home state; whether the shell shows the power menu is shell-local state.

**Keys.** The power key is not configurable: §6.2 names no `config.toml` value for it, and `key_sequence::parse` does not accept the power key names, so no Home, quick-menu or other configured key can be a power key. The adapters bind every plausible code of the remote's ⏻, which is not captured yet: Qt `Key_PowerOff` and `Key_PowerDown` (KWin's long press) on KDE; X11 `XF86PowerOff` on X11/EWMH, where no long press is synthesized, and `XF86PowerDown` where the keymap has it.

**KDE, Plasma 6.7 or later** (owner decision of 2026-10-25). The KWin script registers a third action, `ArinnPower` ("Arinn: Power menu"), without a default key. Its callback runs the Home path (unlocked-session check, remember the Return Activity and output, raise the shell) and reports through `ReportPowerMenuRequest`. When an adapter connection first polls `TakeCommand`, the daemon writes the keys after the Home and quick-menu keys (and after any later Arinn action), so an Arinn action that names a key first keeps it. The takeover needs a KGlobalAccel that stores one key for several actions and triggers the oldest present one: kglobalacceld 6.6.90, which ships with Plasma 6.7. Up to v6.6.0 `GlobalShortcut::setKeys` drops a key any other action stores, present or not ("already taken"), so there the key cannot move without changing PowerDevil's own keys.

1. First the daemon takes a logind `handle-power-key` block inhibitor ("Arinn: the power key opens Arinn's power menu"), so logind never acts on the key either, also without PowerDevil. Without the inhibitor (no logind, polkit refuses) the daemon takes no key at all, the desktop keeps it, and the next attempt follows after 30 s. A take that ends with no key held drops the inhibitor again. It is dropped after the key is given back (below) and at the latest when the daemon exits.
2. For each power key, the daemon asks KGlobalAccel which action holds it (`actionList`). An Arinn action keeps it, and so does any other third-party action: the key is left out and logged as `Conflict`, as for Home (ADR-0094).
3. The daemon writes the free keys and those PowerDevil's `PowerOff` or `PowerDown` hold to `ArinnPower` with `setForeignShortcutKeys`, then reads them back. While PowerDevil's actions are present they are older and still receive the key. `ArinnPower`'s own keys are Arinn's entry in `kglobalshortcutsrc` and are written there like any action's keys.
4. If KGlobalAccel did not store a key PowerDevil holds, it is older than Plasma 6.7. The daemon clears `ArinnPower`, drops the inhibitor and logs `power-key` `Unsupported`; PowerDevil's actions are never set aside, and the desktop's dialog keeps the key. Nothing of KDE's settings is changed.
5. Otherwise PowerDevil's actions are set aside for this KGlobalAccel run only: the daemon calls `setInactive` on each. This marks the action not present, as KGlobalAccel does when an application quits. Nothing about PowerDevil's actions is written to `kglobalshortcutsrc`, and the user's keys for them stay as they are.
6. A failed `setInactive`, a write in step 3 that KGlobalAccel does not answer, or a lookup in step 2 or a read-back in step 3 it does not answer (unknown is never taken as free or empty), rolls the take back, so a present PowerDevil action never shares a key with `ArinnPower` for longer than the take itself: `ArinnPower` is cleared, PowerDevil's actions are made present, and the inhibitor goes once `ArinnPower` is known to be empty (it stays while that is not known). The next attempt follows after 30 s. In step 4 the clearing is checked the same way.

**Only while the shell and the adapter are alive.** Arinn holds the power key only while something can show the menu: the shell is alive while a process owns `org.arinn.Shell1` on the session bus (`arinn-shell.service` is `Type=dbus` with that name), and the platform adapter is alive while it polls (on KDE a `TakeCommand` poll within the last 45 s; the long poll answers within 20 s). The daemon (KDE) and `arinn-platform-x11` (X11/EWMH) follow `NameOwnerChanged` of `org.arinn.Shell1`; the daemon also checks the adapter's last poll every few seconds. When either goes away the key goes back to the desktop at once, as below: a shell at its start limit (5 failures in 60 s, `arinn-session-failed`), a crashed shell, or a KWin script disabled in KWin's settings or lost with `kwin_x11 --replace` while `arinnd` runs. A script that stops polling is noticed within 45 s; until then a press reaches neither Arinn nor PowerDevil. A press between the shell owning its name and its window being ready (about a second at its start) is taken by Arinn but opens nothing yet; the press is lost, never acted on twice, and the next one opens the menu. Waiting for an explicit readiness signal from the shell would need a change to the shell's D-Bus interface, outside this decision. When both are back, the key is taken again; a new adapter connection always writes it again, because a new KWin script registers `ArinnPower` anew. The cases this covers include Close Arinn (a clean exit, which `Restart=on-failure` does not restart), a crash loop, and `arinn-kwin-adapter stop` while `arinnd` runs: the inhibitor goes once the polls stop.

**Giving the key back.** `ArinnPower`'s keys are cleared first, so the desktop is the only holder. PowerDevil's actions then become present again through `setShortcutKeys` with `SetPresent` and autoloading, which keeps the keys KGlobalAccel already stores and writes nothing. The inhibitor is dropped last, so logind stays inhibited until `ArinnPower` no longer holds the key. A release KGlobalAccel does not answer keeps the inhibitor and the key counted as taken, and the next check releases again. The daemon does this when the shell or the adapter is lost, and `arinnd --release-power-key` does it as `ExecStopPost=` of `arinnd.service` (a clean stop, a crash, the start limit) and from `arinn-kwin-adapter stop`, holding a temporary logind inhibitor until `ArinnPower` is cleared and PowerDevil is present, since the daemon's ended with it (Codex on #517). The restore is stateless: it names only PowerDevil's two actions. kglobalacceld loads those actions from `kglobalshortcutsrc` when it starts, so the restore can mark an action present that no running PowerDevil has registered; KGlobalAccel then grabs `Key_PowerOff` for nobody. That is harmless: logind's handling does not change, and KWin only consumes the key event. Independently, KGlobalAccel forgets the inactive state when it restarts, so a new login always starts with the desktop's keys. If kglobalacceld has already exited at logout when the release runs, `ArinnPower`'s keys stay in `kglobalshortcutsrc` next to PowerDevil's. In a session without Arinn the KWin script never registers `ArinnPower`, so it is not present and PowerDevil's action handles the key; the daemon's first check in the next Arinn session, before any shell is alive, gives the key back and clears that entry. This depends on how kglobalacceld (6.6.90 or later stores a key for several actions and triggers the oldest present one) loads such duplicates, which the operator test checks after a logout; the fallback, giving the key back, is safe either way.

**X11/EWMH.** Never on the ordinary XFCE desktop: there xfce4-power-manager keeps the key and its dialog, also when Arinn starts first and could win the X grab (owner decision of 2026-10-24). The adapter recognises XFCE on the session bus, not from the environment: an XFCE desktop is one where `org.xfce.SessionManager` (which ADR-0107 already waits for) or xfce4-power-manager's `org.xfce.PowerManager` has an owner. `XDG_CURRENT_DESKTOP` cannot decide it, because `arinn-ewmh.service` gets its environment from the user manager and the opt-in bridge imports only `DISPLAY` and `XAUTHORITY`; on distributions whose X session scripts do not import the whole environment (Arch's `50-systemd-user.sh`) it never reaches the unit (reviews of #516 and #517). So:

- **An XFCE name on the bus, no `ARINN_SESSION_ENTRY=xfce`:** the ordinary XFCE desktop, or another desktop where xfce4-power-manager runs and grabs the key. The key is never taken.
- **`ARINN_SESSION_ENTRY=xfce`:** the dedicated Arinn XFCE session, whose wrapper exports the marker to the user manager ([ADR-0107](0107-dedicated-arinn-session.md)). The key is taken as below. The marker is bound to the current login (Codex P1 on #516): the wrapper also exports it into the desktop session's own environment, and the XFCE launcher (`arinn-xfce-session`), the only starter of the EWMH target on XFCE, mirrors that environment into the user manager before it starts the target: it sets the marker when its login carries it and clears it otherwise. A marker a killed wrapper left in a lingering user manager (lingering, SDDM `Relogin=true`, another open session) is therefore cleared by a stock XFCE login with the opt-in autostart, and that ordinary desktop keeps its key and its dialog.
- **No XFCE name:** any other X11/EWMH desktop takes the key as below.
- **An XFCE name that appears later** (xfce4-power-manager started while Arinn runs): the adapter checks both names with the shell's on every pass of its loop (at least every 500 ms) and gives everything back. xfce4-power-manager grabs the key once, when it starts and before it owns its name, with any modifier on the root window; while Arinn holds the grab that fails with an asynchronous `BadAccess` it ignores, and it never grabs again (`xfpm-button.c`). So when Arinn lets go of a grab while xfce4-power-manager runs and no client grabs a mapped power key (with none mapped there is no grab to repair), the adapter restarts xfce4-power-manager through its own D-Bus `Restart` (`org.xfce.PowerManager`, `/org/xfce/PowerManager`, `org.xfce.Power.Manager`) and logs it; the new instance grabs the key and the desktop handles it again. The restart runs off the adapter's loop, which goes on at once; logind's inhibitor (Arinn's own, or a temporary one at a start) is held until the new instance owns its name (at most 15 s). It never restarts an xfce4-power-manager that holds its grab, or one that was not running when Arinn let go (it grabs when it starts). The same check runs at the first pass of every adapter start (an earlier adapter may have crashed while it held the grab) and in `arinn-platform-x11 --release-power-key` (`ExecStopPost=`, which holds a temporary logind inhibitor while it gives the XFCE setting back and restarts xfce4-power-manager, since the adapter's ended with it), but there only when this X display's adapter held a power grab: while grabbing, the adapter keeps a marker naming its display in `$XDG_RUNTIME_DIR/arinn/power-grab`, removed once the check after letting go has run. The dedicated session and the ordinary XFCE desktop never grab, so they never restart xfce4-power-manager. A restart ends the old instance, so idle inhibitors applications held through it are lost; normally the instance restarted is about half a second old, and only a crash in that window meets an older one. Giving the key back at once, rather than keeping it until Arinn stops, follows the owner's rule that a desktop with xfce4-power-manager keeps its dialog, and needs no restart at the end of a crash. Arinn and the desktop never both act on one press, and the key is never left to nobody.

Every adapter connection starts with the power keys neither grabbed nor read; only this decision turns them on. While the shell owns `org.arinn.Shell1`, the adapter first takes the logind inhibitor, then `arinn-platform-x11` grabs the power keys on the root window after the Home and quick-menu keys (outside the dedicated session; there it never grabs, below), also while the shell has focus. A power key that is also a Home or quick-menu key is left out, so they win. A press reports `ReportPowerMenuRequest` after the same unlocked check as Home and raises the shell as Home does. Without the inhibitor nothing is grabbed (a retry follows after 30 s). When the shell's name loses its owner, the grab or raw reading stops working or changes (a regrab after a mapping change lost it) or the adapter's session ends, the adapter releases the grab, the raw-event selection, the XFCE setting below and the inhibitor, in that order, and takes them again when the shell is back. A key another client holds (`BadAccess`, for example xfce4-power-manager) is skipped and logged; it never stops the adapter, and the desktop keeps the key.

**XFCE, dedicated Arinn session only** (owner decision of 2026-10-24). When the adapter runs with `ARINN_SESSION_ENTRY=xfce` (the dedicated session of [ADR-0107](0107-dedicated-arinn-session.md)) and the shell is alive, the adapter never grabs the power keys: it reads them from XInput2 raw key presses (`XI_RawKeyPress` on the root window, XInput 2.1 or later; repeats ignored), with the logind inhibitor taken first. xfce4-power-manager's own grab therefore succeeds whenever it starts, before or after Arinn (review of #516). Only once raw reading works does it set xfce4-power-manager's `/xfce4-power-manager/power-button-action` (xfconf channel `xfce4-power-manager`) to 0, "do nothing", through xfconf's D-Bus API; xfce4-power-manager keeps its grab but no longer acts on the key. Without XInput 2.1, or when xfconf refuses, nothing is set or read, and the key stays the desktop's. Without xfconf the dedicated session takes nothing. A raw press read before xfconf confirmed "do nothing" belonged to xfce4-power-manager and is dropped; only later presses open Arinn's menu. Raw events report every key press of the session to the adapter; it looks only at the keycodes of the power keys, and keeps and logs nothing about any other key (§13). The rules that keep the user's value:

- Before any change the user's value is written durably to `$XDG_STATE_HOME/arinn/xfce-power-button`: a `uint` or `int` the user set, or "not set". xfconf's `GetProperty` also returns a system default from `XDG_CONFIG_DIRS` when the user never set the property, so the adapter reads the live value over xfconf's D-Bus API and takes it as the user's when the user's own channel file (`$XDG_CONFIG_HOME/xfce4/xfconf/xfce-perchannel-xml/xfce4-power-manager.xml`) names the property, or when it differs from the system default (the first `XDG_CONFIG_DIRS` channel file that names it, otherwise xfce4-power-manager's built-in "do nothing"). Only a live value equal to the system default is recorded as "not set" and given back with `ResetProperty`, never pinned as a user value. xfconfd writes the user's file a few seconds after a change, so the comparison is what recognises a value the user set just before Arinn took the key (Codex P2 on #516); a user who set exactly the system default gets it back as the default. Without that copy nothing is changed; a value of another type, a locked property or a missing xfconf (neither running nor activatable) changes nothing either, and the key stays the desktop's.
- The copy is given back, and only then removed: when the shell is lost; on a clean stop of the adapter; from `ExecStopPost=` of `arinn-ewmh.service` (`arinn-platform-x11 --release-power-key`, which also covers a crash and the start limit); at the next start of the adapter in any X11/EWMH session; and at every XFCE login, by a system XDG autostart entry, `/etc/xdg/autostart/org.arinn.PowerButtonRestore.desktop` (`OnlyShowIn=XFCE;`, `arinn-platform-x11 --restore-power-button`). That entry covers an unclean end of the dedicated session (a power cut, a reset, a killed user manager) followed by a plain XFCE login, where no Arinn code runs otherwise. It does nothing without a copy, starts no part of Arinn (ADR-0042 is unchanged), and does nothing while the adapter owns `org.arinn.X11`; a lock file next to the copy orders it with the adapter's own take and release, so in the dedicated session it either runs before the adapter takes the key or leaves the key alone. A take that finds a copy first gives it back as a release does, and only then reads the current value: a value the user chose since (for example in the plain desktop after a power cut) is theirs and survives, and Arinn's own "do nothing" is never read as the user's value.
- The restore survives removing the package (review of #516, Codex P1): together with the copy, before the setting changes, the adapter writes a per-user XDG autostart entry, `$XDG_CONFIG_HOME/autostart/arinn-power-button-restore.desktop` (`OnlyShowIn=XFCE;`), and a small `sh` script next to it that holds the value. It uses only `sh` and XFCE's own `xfconf-query`, so it works without any part of Arinn. The script names the adapter binary that wrote it (its own path, so an install outside `/usr` or a development build counts too; an upgraded file's " (deleted)" suffix is dropped). While that binary exists the script does nothing, and the adapter and the system entry above restore the value with their lock. Once it is gone, at the next XFCE login the script gives the value back (a `uint` or `int` with `xfconf-query --create --type`, "not set" with `--reset`) only if the setting still holds "do nothing", and then removes itself, the script and the copy. A setting it cannot list or read keeps everything for the next login; a property no longer listed (the user reset it) only removes them. Every release removes the entry with the copy. Without the entry (it cannot be written, or a path needs quoting the entry cannot express) nothing is changed and the key stays the desktop's. The entry goes to `$XDG_CONFIG_HOME/autostart` as the adapter sees it, from the user manager. An `XDG_CONFIG_HOME` set only in the login environment and not in the user manager puts it where XFCE's autostart does not look; then only the system entry restores the value, and a removal before that login leaves "do nothing" until the user picks an action. The defaults agree, and the packages set neither.
- When the setting no longer holds "do nothing" at release time, the user changed it while Arinn ran; that value is kept and the copy dropped. A user value of "do nothing" needs no change and no copy. A user who chooses "do nothing" in *Power Manager* while Arinn runs (the dialog already shows it) cannot be told apart from Arinn's value and gets the earlier value back when Arinn stops.
- The ordinary XFCE desktop with opt-in autostart (no `ARINN_SESSION_ENTRY`) is never changed; there the desktop keeps the key and its dialog, and only a copy left by an earlier dedicated run is given back.

The desktop and Arinn never both act on one press.

**Shell.** The shell subscribes to `PowerMenuRequested` before it reads `Status` and handles a request only for the current daemon owner and epoch. It ignores the request while its session guard blocks it (locked, or the lock state unknown). It ends ambient without a consumed wake, then opens the power scope ([ADR-0108](0108-system-control.md)) over what it shows: over an Activity that is Home, as for the Home key. A quick menu over an Activity gives way to Home first, as for the Home key; a quick menu over the shell keeps the sheet under the power scope, as its own Power row does. An open power scope stays as it is, including a confirmation or a request in flight. Back and Cancel close the scope and leave the shell where the request put it.

## Consequences

- The power key reuses the Home presentation path: lock check, Return target, output and the Activity background. Only the request that names the intent is new.
- An old shell ignores `PowerMenuRequested`; with a new adapter the key then shows Home. An old daemon answers `UnknownMethod`, and the KWin script shows nothing. Adapter, daemon and shell are installed together.
- The computer's own power button sends the same `KEY_POWER` as the remote, so while Arinn holds the key it also opens Arinn's power menu, and on the lock screen it does nothing at all: Arinn opens nothing there (§5.7), and PowerDevil's action, xfce4-power-manager's action in the dedicated session, and logind are all set aside. Only the firmware's long press (a hard power-off after about four seconds) still works there. Once the shell or the adapter is gone, the desktop's handling is back on the lock screen too.
- On Plasma before 6.7, including the Plasma 6.3–6.5 targets of [ADR-0105](0105-global-on-screen-keyboard-platform-text-delivery.md), the ⏻ key keeps the desktop's power dialog while Arinn runs, and Arinn logs `power-key` `Unsupported`; the power menu is still reachable from the shell. Nothing of KDE's settings is changed there.
- A long press of the remote's ⏻ on KDE/Wayland opens the power menu too, instead of PowerDevil's long-press action.
- A PowerDevil restart registers PowerDevil's actions present again, and KGlobalAccel then triggers the older of the two actions, normally PowerDevil's. The daemon follows PowerDevil's bus name `org.kde.Solid.PowerManagement`: when it gets a new owner, the daemon takes the key again at once and after 5 and 30 s, since PowerDevil registers its actions only after it owns the name (review of #516, Codex P1). A tablet-mode change also registers PowerDevil's `PowerOff` again without a new bus owner; until the next adapter connection the desktop then handles the key. Either way Arinn and the desktop never both act on one press.
- A hung (not crashed) daemon or shell keeps the key: the shell's bus name stays owned and a hung process does not release anything. No Arinn unit sets systemd's `WatchdogSec=` (the daemon and the shell send no watchdog keep-alives), so systemd does not turn a hang into a restart. Until the process is stopped or the session ends, a press opens no menu; the firmware's long press still powers off.
- In the dedicated Arinn XFCE session the key opens Arinn's power menu; the user's xfconf value is out of effect only while Arinn runs there. A power loss leaves "do nothing" in xfconf until the next XFCE login, whose autostart entries restore it (also after Arinn was removed), or the next start of the adapter. The ordinary XFCE desktop keeps the desktop's handling of the key. On another X11/EWMH desktop without xfce4-power-manager Arinn owns the key and logind's default power-off is inhibited.
- A key Qt cannot name still cannot be a global shortcut; udev hwdb remapping remains the workaround (ADR-0094).

## Alternatives considered

- **A presentation kind on a generic request.** Rejected in ADR-0106 and on #467: the shell would dispatch on a string the daemon must still validate.
- **Infer the power menu from `Changed` or `Status`.** Forbidden by ADR-0069.
- **Move PowerDevil's key to `ArinnPower` with `setShortcutKeys` and restore it on exit.** Would work before Plasma 6.7 too, but writes the user's `kglobalshortcutsrc` twice per run, and a crash before the restore leaves the change in the user's configuration, also for the plain desktop session. `setInactive` reaches the same result without writing a setting, from Plasma 6.7 on. The owner chose on 2026-10-25 to support only Plasma 6.7 or later rather than change KDE's settings on older Plasma.
- **Set PowerDevil's *When power button pressed* to *Do nothing* while Arinn runs.** Changes `powerdevilrc`, a user setting, and PowerDevil would still hold the key, so `ArinnPower` could not receive it.
- **Switch PowerDevil's KGlobalAccel component to another shortcut context.** Also session-only, but it disables every PowerDevil key (sleep, brightness), not only the power key.
- **Only a logind inhibitor.** Stops logind, not PowerDevil or xfce4-power-manager, which react to the key themselves.
- **Change xfce4-power-manager's `power-button-action` in every XFCE session Arinn runs in**, the opt-in autostart included. Rejected by the owner on 2026-10-24: the ordinary desktop keeps its dialog.
- **Set `logind-handle-power-key` instead.** The same persistence, and whether xfce4-power-manager then releases its X grab depends on its version.
- **Restore the value from the session wrapper** (`arinn-session`) before a plain desktop login. Not enough: a plain XFCE login does not go through the wrapper at all. The XDG autostart entry runs in every XFCE login instead.
- **Tell the ordinary XFCE desktop apart by `XDG_CURRENT_DESKTOP`.** The variable does not reach `arinn-ewmh.service` on every distribution, and without it every X11 session would look like a desktop without a power manager (review of #517).
- **Take the key on X11/EWMH only in the dedicated session.** Simple, but it would drop §5.7 on every other EWMH desktop, an MVP platform, without an owner decision (review of #516). XFCE's bus names tell the ordinary desktop apart instead.
- **Tie the takeover to the daemon's or the adapter's lifetime only.** A shell at its start limit or an unloaded KWin script would leave the key with Arinn while nothing can show the menu (review of #516).
- **Listen without owning the key** (KGlobalAccel's `globalShortcutPressed` on PowerDevil's component, XInput2 raw events). The desktop would still act on the same press.
